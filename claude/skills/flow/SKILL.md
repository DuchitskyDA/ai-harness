# Эпик

Отвечай по-русски. Не проводи повторное интервью: используй решения владельца и тикеты в `epic.md`. Цель неясна, третий прогон или повторный отказ приёмки — раздел «Повтор, возврат и выход из цикла».

Порог — один worker: больше пяти файлов кода или две области (API и экран) — это эпик. Эпик также — работа, которую владелец назвал эпиком, или задача, в которой появился второй тикет. Одиночная задача, в том числе рискованная, идёт основным потоком по своду; раздел «Решения владельца» действует и для неё. Эпик ведёт главная сессия в `<specs>/<проект>/<эпик>/epic.md` (формат — `grill-with-docs`), спеки тикетов — `<тикет>.md` рядом; новая сессия продолжает по `epic.md`.

Git: обычные Git-действия разрешены постоянным поручением пользователя. Для destructive или чувствительных операций запрашивай подтверждение, если задача явно их не охватывает. В `my-app` — ограничения свода, «Исключение my-app». Читай проектные инструкции. Нечувствительные production и инфраструктурные изменения выполняй автономно в пределах задачи.

## Маршрут эпика

сборщики → грилл → связка (главная сессия) → нарезка по связке (`to-tickets`) → спека тикета (его worker) → новые продуктовые дельты владельцу → ультракод по волнам с ревью каждого тикета → итоговая приёмка Codex → разбор архитектуры

1. **Сборщики.** Факты собирают Claude `researcher` (Haiku 5.5, простой поиск) и `auditor` (Sonnet 5.5, чтение кода); независимые области — параллельно. Сборщик возвращает факты с адресами путь:строки, без выводов. Анализ делает главная сессия.
2. **Грилл.** Обсуждение и грилл идут в чате. Грилл пропускается, если решения владельца уже явные (выбранный макет, решение в чате): `epic.md` рождается с этими решениями дословно и датой. Иначе — `grill-with-docs`; после общего понимания — `epic.md`, затем `to-tickets`: сначала связка, по ней нарезка.
3. **Тикеты и ветки.** Ветки и PR эпика — POLICY, «PR», пункт «Эпик»: ветка эпика `<эпик>` от основной, ветка волны `<эпик>-w<N>` от ветки эпика, PR волны в ветку эпика (сливает владелец), в конце PR эпика в основную со ссылками на PR волн. В эпике из одной волны «ветка волны» ниже — сама ветка эпика, PR волны нет. Каждая задача flow — своя тематическая ветка; id тикетов понятные. Тикеты не пересекаются по изменяемым файлам. Параллельные правки одного репозитория — в отдельных рабочих копиях; создаёт и сажает их главная сессия обычным Git. Копию исполнителя создавай от ветки волны: `git worktree add -b <ветка-задачи> <путь вне .claude/worktrees> <эпик>-w<N>`, путь — в задаче исполнителя. Agent `isolation: "worktree"` не используй: Claude Code создаёт такую копию от main, а не от HEAD, и удаляет её, когда агент останавливается без правок. Ветку задачи называй `<эпик>-<тема>`: при существующей ветке `<эпик>` git не создаст ref `<эпик>/<тема>`. Занятую копию не переключай, чужое не stash и не откатывай.
4. **Порядок волны:**
   связка → нарезка по связке → спеки тикетов → реализация.
   Связку и нарезку ведёт главная сессия; спеку тикета и реализацию — worker этого тикета (п. 5–6, «Исполнение»).
   До запуска worker главная сессия сверяет связку и каждую её правку с решениями владельца в `epic.md` по пунктам; расхождение исправляет в связке до нарезки и спек: ошибку входа автор спеки переносит в спеку, а не ловит.
5. **Спеки.** Связку пишет сама главная сессия, спеку тикета — его worker до кода, в том же контексте, где потом реализует; обе по to-tickets, «Спеки волны». Спека тикета — файлом `<тикет>.md` рядом с `epic.md`.
6. **Без ревью плана.** Отдельного ревью связки и спек нет. Связку с решениями владельца сверяет главная сессия (п. 4). Спеку тикета worker читает до кода: строку «Риск:» и противоречие со связкой, base или решениями владельца возвращает главной сессии и ждёт решения. Расхождение кода со спекой ловят ревью тикета и итоговая приёмка.
7. **Дельты владельцу.** После спеки предъяви владельцу новые продуктовые дельты по разделу «Решения владельца». Дельту из спеки тикета worker возвращает главной сессии и ждёт выбора: вне T3 ответ — через SendMessage, в T3 — `t3_thread_send` в его тред.
8. **Ультракод** — по разделу «Исполнение»: связка — после «да» на неё, код тикета — после его спеки и выбора владельца по его дельтам.
9. **Ревью тикета** — раздел «Ревью тикета».
10. **Итог** — раздел «Итоговая приёмка», затем «Разбор архитектуры».

## Решения владельца

- Продуктовая дельта — запись «было → будет → последствия»; владелец выбирает её до кода. Это относится и к одиночной задаче.
- Молчание, вопрос владельцу и встречный вопрос — не выбор. «Продолжай с допущением» разрешает только техническое решение.
- Технические решения принимай сам и называй в отчёте; повторным гриллом их не делай.
- Принятый выбор сразу — в `epic.md` (одиночная задача — в спеку) дословно с датой. Следующий шаг записывай сразу, а не в конце сессии.
- Ранее принятое и всё ещё актуальное согласие повторно не запрашивай: сверь его с актуальным планом.

## Исполнение

1. Ультракод — в той же сессии. Включение штатное: ultracode в запросе или `/effort ultracode`; скрипт-раннер не создавай. Слово в тексте скилла или в task дочернего агента режим не включает: запуск — штатный Workflow главной сессии по схеме, которую показывает инструмент. Инструмента нет — сообщи ограничение наверх, без вложенного CLI и самодельной эмуляции.
1a. На каждый тикет — один `worker`: в поручении тикет, путь к `epic.md`, base и копия; спеку он пишет сам (п. 5–7 «Маршрута эпика»), затем реализует и ревьюит («Ревью тикета»). В T3 исполнители (`worker`, `mechanical`) — дочерние треды, а не Workflow: главная сессия запускает каждого через `delegate_task` по POLICY, «Роли и модели», с `isolation: "worktree"` — копия от текущего коммита главного треда, поэтому главный тред стоит на ветке волны; независимые — несколькими вызовами `mode: "async"` сразу. Ветку и дифф каждого видно в панели T3. Дифф исполнителя — в его worktree (`worktreePath` из `t3_thread_read` по `childThreadId`); сажает главная сессия. Вне T3, а также по прямому «ultracode» владельца — Workflow и копии по п. 3 «Маршрута эпика».
2. Исполнитель один — Opus high, effort по тикету — POLICY, «Роли и модели»; mechanical — Sonnet low, только для готовой механики. Полосы worker и complex описывают сложность спеки, а не отдельный профиль: сложную реализацию делает тот же исполнитель.
3. Связное — одному агенту; независимое — параллельно, если не пересекаются файлы, контракты, хосты и ресурсы. Номер волны не барьер: зависимый тикет стартует после принятия своей зависимости — из другой волны это слияние владельцем её PR волны в ветку эпика; спеки следующей волны идут во время реализации текущей. Задача исполнителю — тикет, base, владение файлами, запреты и проверки области.
4. Проверки исполнителя — только область, результат каждой команды различим; код и тесты — по Skill `ub-mode`. Общие проверки (typecheck, lint, test на всё приложение) делает главная сессия, по одной на машину. Лимит параллели — из конфигурации проекта.
5. Продуктовый выбор внутри Workflow: агент останавливает зависимую работу до правки и возвращает вопрос, варианты и последствия. Независимые ветки заканчивают разрешённое. Workflow не ждёт ввода посередине: после возврата главная сессия задаёт вопросы владельцу и записывает ответы в `epic.md`.
6. Дозапуск: путь скрипта и run id — в `epic.md`; затем тот же Workflow с параметром `resumeFromRunId` и ответами владельца, в той же сессии. Это параметр штатного Workflow, не shell-команда; другие параметры не выдумывай — до вызова сверь схему инструмента.

## Ревью тикета

Каждый тикет до посадки ревьюит его worker: Codex adversarial (gpt-6.1-sol, xhigh) на свой дифф против base, до 3 раундов. Задание, раунды, журнал и сдачу worker ведёт по своему профилю (`claude/agents/worker.md`, «Ревью тикета»): правила там, потому что профиль worker видит всегда, а flow открывает не всегда. Отдельного ревью волны нет. Главная сессия получает дифф, последний вердикт Codex, журнал и путь `last-<run>.md`; сбой Codex — код и путь, решает главная сессия.

Задание Codex adversarial на итоге — нейтральное, как у worker на тикете: scope, пути, задуманное поведение, base, diff и вывод проверок. Без подозрений и гипотез, без ожидаемого вердикта, без находок другого ревьюера; журнал своих прошлых раундов — можно. Включи дословно: «В итоговом ответе оцени каждую находку от 1 до 10 — как часто она случится — и от 1 до 10 — насколько это плохо».

## Запуск Codex

adversarial и ops запускает главная сессия, adversarial на тикет — его worker. В T3 — `delegate_task` по POLICY, «Роли и модели»: модель и effort из профиля роли, `serviceTier: "priority"` только у ops (adversarial без Fast), `developer_instructions` профиля в начале `task`, запись итога в `last-<run>.md` в конце, у главной сессии `mode: "async"` и таймер 7200 с с `task_cancel`, у worker — `mode: "wait"` с `timeoutMs: 7200000`, чтобы он ждал Codex вживую, а не уходил в idle; ход виден владельцу в дочернем треде. В T3 `codex.py` не используй — ни главная сессия, ни worker, ни в поручении исполнителю. Вне T3:

`python -X utf8 -B ~/.harness/codex.py --role adversarial|ops --task <UTF-8-файл|-> --cwd <каталог> [--timeout <секунды>] [--sandbox read-only|workspace-write|danger-full-access] [--out-dir <каталог>]`

- `--task` и `--cwd` обязательны; task с нужной спекой и контекстом готовит тот, кто запускает.
- По умолчанию timeout 7200 (только больше 0), sandbox danger-full-access. Findings — `%LOCALAPPDATA%/harness/findings` или `~/.local/state/harness/findings`, подкаталог роли; свой каталог — `--out-dir`.
- Выход: уникальный run, `live-<run>.log` и `last-<run>.md` абсолютными путями. Коды: 0 — непустой last; 2 — аргументы или профиль; 3 — запуск, сбой Codex или нет ответа; 124 — таймаут; 130 — отмена.
- Код не 0 или пустой ответ — отчёт с кодом и путями, а не состоявшееся ревью; без подмены профиля.
- Запускай фоновой задачей: прогон идёт минутами.

## Повтор, возврат и выход из цикла

Память эпика — `epic.md`, уроков — память Claude; других трекеров и планов не заводи.

1. Перед любым повтором сверь `epic.md`, base и изменения, спеку тикета и незавершённые побочные эффекты. Устаревшее разрешение на другой план или тикет не применяй.
2. Resume Workflow может заново выполнить завершённые агенты после изменённого или неуспешного места: exactly-once не обещай. Агент сверяет свою прежнюю работу и делает только недоделанное.
3. Новая сессия без прежнего run — новый прогон по `epic.md`, не resume старого. Журнала нет или resume упал — скажи об этом явно, без молчаливого полного рестарта.
4. Цель неясна: прочитай цель, факты кода и `epic.md` адресно. Каждое неизвестное — вопрос, варианты, нужные факты и критерий решения в `epic.md`. Факта нет — сборщик; решение влияет на результат — `grill-with-docs`. Принятое повторно не обсуждай.
5. Третий прогон или доработка по одному тикету, повторный отказ приёмки или откат своей правки — стоп: факты в `epic.md` и вопрос владельцу о новом продуктовом выборе; новый пустой тикет не заводи.

## Итоговая приёмка

Итог эпика — Codex adversarial (gpt-6.1-sol, xhigh), всегда, на одноразовой копии `git worktree add --detach <путь> <коммит>`; после ответа копию удаляет главная сессия (`git worktree remove --force`). Главная сессия даёт ему base, diff, `epic.md`, вывод проверок и команду тестов области через task — нейтрально, по «Ревью тикета»; запуск — раздел «Запуск Codex», `--cwd <копия> --sandbox workspace-write`: в копии он гоняет тесты и мутации. В задании: pytest — с `-p no:cacheprovider --basetemp=<копия>/.pytest-tmp`, ruff — с `--no-cache`: системный temp и кэш песочнице Windows недоступны. Если ticket один, его ревью тикета и есть итоговая приёмка.

adversarial проверяет:

- все критерии приёмки и отсутствие scope creep;
- контракты между tickets, миграции, порядок зависимостей, ошибки интеграции;
- пересечения файлов, данных, хостов, окружений и общих ресурсов;
- качество, безопасность и эксплуатационные риски;
- вывод интеграционного прогона главной сессии.

Находки — только то, из-за чего работа не принимается: путь:строка, почему это ошибка, команда или тест, показывающие поломку, требуемое действие. Пожелания и стиль — не находки. Находки разбирает главная сессия: каждую подтверждает или отклоняет с адресом и доказательством, маловероятное и вне scope — строкой; блокирует подтверждённое. Сбой Codex — код и лог в `epic.md`, приёмка названа несостоявшейся. Подтверждённые дефекты правятся в scope тикета, посторонние — строкой владельцу и в `epic.md`; после исправлений — новый раунд adversarial с журналом прошлых находок, до 3 раундов.

### Артефакт-подтверждение

Делай, только когда есть на что смотреть: схема устройства, экран, сравнение. Публикует главная сессия инструментом Artifact приватно.

- Схема — картинка `<img src="data:image/svg+xml;base64,…" alt="<что на схеме>">` с width и height в px у корневого `<svg>`. Подписи целые — проверь на снимке страницы.
- Данные — фактические команды, их вывод и артефакты этого прогона (снимки до и после).

Секретов и персональных данных в артефакте нет. Ссылка — в ответе владельцу и строкой `артефакт: <ссылка>` в `epic.md`.

## Разбор архитектуры

После PASS итоговой приёмки главная сессия по Skill `ub-mode` («Architecture», «Then Make it Right») проходит область эпика: мелкие модули, лишние швы, связность, которую эпик нарастил. Код не меняет. Кандидаты (путь:строка, что углубить, выигрыш) — разделом «Архитектура после эпика» в `epic.md` и строкой в ответе владельцу: что из этого брать, решает он. Кандидатов нет — строка в `epic.md`.

## Коммит и закрытие

- Коммит — обычный `git commit`; проверки подключены локальным неотслеживаемым pre-commit проекта. В staging — только свои файлы; непроверенное не выдавай за зелёное.
- Исполнитель не коммитит и не сажает копию. Главная сессия проверяет, интегрирует обычным Git в ветку волны, затем ставит тикету статус и итог в `epic.md` по критериям, подтверждённым терминальным выводом.
- `install.py --apply` — главная сессия, в основной копии, после слияния в основную, менявшего профили, правила или скиллы.
- До закрытия эпика перенеси уроки в память Claude. Кандидаты — строки «урок» в `epic.md` и находки приёмки по определению урока в POLICY.md («Решения и доки»). Урок — файл памяти «когда — что делать — почему» и строка в `MEMORY.md`; тема уже есть — дополни её файл. В `epic.md` — `уроки: перенесено N, файлы: ...` и статус эпика.

## Разговор и темп

Автономия и блокирующие вопросы — по своду; грилл по grill-with-docs ждёт ответа владельца.

Выбирай способ исследования по нужному доказательству, читай экономно и ограничивай вывод у источника.

Для длинного вывода нужна доказательная сводка по всему объёму: счётчики, первые уникальные ошибки, путь к полному логу; способ подготовки выбирает исполнитель.
