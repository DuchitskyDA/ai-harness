# Нарезка эпика

Отвечай по-русски. Работай от `epic.md` после грилла и реального репозитория. Не проси утвердить каждый ticket и не создавай других файлов планов. Грилл уже согласован — повторного согласования не требуй.

1. Изучи владельцев модулей, импорты, API/схемы, тесты, конфигурации, затрагиваемые пути, хосты, окружения, базы, очереди и общие ресурсы. Чувствительное изменение требует разрешения с действием, целью и границами; статус production сам по себе чтение и безопасную работу не запрещает.
2. Сначала напиши связку волны — раздел «Спеки волны», шаг 1, — затем режь по ней: шов, контракты и имена берёшь из связки и не придумываешь заново. Раздели работу на минимальные проверяемые tickets и проектируй разрез под параллель; шов выделяй при общем изменяемом контракте. Допускай реальные зависимости между самостоятельно проверяемыми результатами. Не режь по этапам и слоям (модель → API → UI → тесты): такие tickets пересекаются почти всегда и выстраиваются в цепочку. Общий файл, который трогали бы несколько срезов (реестр, роутер, перечень, barrel, общий тестовый стаб), целиком отдай шву или заключительному ticket; каждый изменяемый файл принадлежит ровно одному ticket. Механическое широкое изменение и перенос модуля дели expand → migrate → contract: шов создаёт новое место и оставляет в старом реэкспорт, срезы переводят своих потребителей, снос старого — заключительный ticket; так промежуточные tickets остаются проверяемыми. Режь по волнам: волна — tickets, которые идут параллельно и не пересекаются по изменяемым файлам, контрактам и импортам изменяемых модулей, а барьер между волнами — только реальная зависимость: тикет следующей волны стартует, как только приняты тикеты, чьи файлы или контракты он использует; зависимость пиши у тикета в `epic.md`, иначе тикет считается независимым и идёт сразу. Полоса описывает полноту решения в спеке: `mechanical` — правка, данная спекой готовой, в любом числе файлов; `worker` — новая логика до пяти файлов кода, место и решение названы (новые модули от выноса в счёт не идут), включая шов волны и финал экрана по выбранному макету; `complex` — решение спека назвать не может: диагностика, макеты экрана, стык областей. Модели исполнителей — из профилей и решения эпика, не из полосы.
3. Ticket — только работа, которую владелец захотел бы видеть в списке; находки, риски и открытые вопросы пиши в `epic.md` («Границы и риски»), а не отдельными тикетами. Тикеты пиши в `epic.md`, раздел «## Тикеты (волна N)»: по каждому — `### <id> — <тема> (<полоса>)` с понятным id (ветка `<эпик>-<id>`), **Владение** (каждый изменяемый файл — ровно одному тикету), **Будет** (что хотим получить и как будем делать), **Критерии приёмки**, **Проверка**, **Границы и риски**, зависимости и, если ticket шире `worker`, почему. Строку тикета добавь в «Статус тикетов» (`| тикет | статус | итог |`). Общий контекст не копируй — он в «Было → будет». Не включай исходный код; точные пути и ресурсы полезны, когда определяют область работы.
4. Добавь реальные blocking-зависимости. Tickets можно исполнять параллельно только при отсутствии пересечения по изменяемым файлам/модулям, контрактам, хостам, окружениям, данным и общим ресурсам. Любое пересечение делает их последовательными или требует отдельного интеграционного ticket. Общий импорт сам по себе не зависимость; учитывай изменение используемого контракта. Зависимость среза от среза, а не от шва, записывай только с адресом связности — путь:строки общего файла или контракта; порядок этапов основанием не считается. Число строк и файлов — ориентиры; границы определяют связность результата и проверяемость. У каждого ticket укажи команду проверки только по его области: тесты по тронутым путям, lint по изменённым файлам; с различимым результатом каждой команды. Тест в тикете — по Skill `ub-mode`; тяжёлый тест — только исключением с причиной в тикете. Полные проверки — typecheck, lint и test на всё приложение — в срезы не ставь. Подготовка (codegen, prisma generate, build пакета контрактов) — не проверка: называй её отдельным шагом постановки исполнителя.
5. Для нескольких независимых срезов создай заключительный ticket интеграционной проверки, зависящий от дочерних tickets: полные проверки — typecheck, lint и test на всё приложение — идут только в нём, по одному на машину. Волну принимает оркестратор по критериям tickets командами; интеграционную проверку ставь по реальным зависимостям, а не после каждой посадки. Отдельный тикет на приёмку не заводи. Для одной задачи включи интеграционную проверку в её приёмку без отдельного ticket.
6. Запиши в `epic.md` карту зависимостей: tickets по волнам и шагам, ширину фронта каждой волны (сколько tickets идут параллельно) и длину критического пути, с обоснованием параллелизма. Номер волны основанием для blocking не служит; длину критического пути определяют реальные зависимости, у каждого звена — адрес связности. После этого передай в `flow` готовую волну по разделу «Спеки волны» ниже.
7. Тикет рискованного домена (деньги, права, миграции и чувствительные области по POLICY.md) — с пометкой risky в заголовке; в нём — доказательство регрессии: тест, причина падения на base, команда проверки и ожидаемый итог после правки. Требование видно в тикете до кода.

## Спеки волны

Спека волны идёт в два шага: меньше охват — точнее спека, тикеты пишутся параллельно. Порядок волны:
связка → нарезка по связке → спеки тикетов → реализация.
Отдельного ревью плана нет: связку с решениями владельца в `epic.md` сверяет главная сессия, противоречие спеки со связкой ставится первой строкой «Риск:» и решается до кода.

Связку и нарезку по ней пишет главная сессия (шаг 1), спеку тикета — worker этого тикета до кода (шаг 2). Спека задаёт решения без тел функций; код не меняется, пробы — только во временной копии base. Спеку тикета worker сохраняет в `<specs>/<проект>/<эпик>/<тикет>.md` рядом с `epic.md` (specs — POLICY, «Процесс») и отчитывается главной сессии; `epic.md` правит только главная сессия.

Шаг 1, связка и нарезка: главная сессия сначала пишет в `epic.md` раздел «## Связка (волна N)», до ~25 строк: шов и контракты (путь:строки в base), единые имена функций, флагов, файлов и ключей. Затем по связке — раздел тикетов волны N по п. 2–7: владение файлами (каждый изменяемый файл — ровно одному тикету), зависимости с адресом связности, полоса каждого тикета. Спеки тикетов не пишет. Решения владельца и «Было → будет» не меняй и не перезаписывай.

Шаг 2, тикет: worker читает в `epic.md` решения владельца и свой тикет волны N и пишет спеку только своего тикета. Архитектура — из связки: шов, имена, владение файлами и контракты бери дословно, не придумывай заново и не переразрезай; своё решение — только внутри файлов тикета. Обязательно в спеке тикета:
- контракт входов и выходов — что тикет получает от шва и соседей и что отдаёт: сигнатуры, поля, форматы, коды выхода;
- конкретные файлы и интерфейсы — путь:строки в base и новые модули, только из владения тикета по связке;
- критерии приёмки и граничные случаи — проверяемые командой, с таблицей «ситуация → ожидаемо» для состояния и командой проверки области: волну принимают именно по ним;
- зависимости от других тикетов — от чего тикет зависит и кто зависит от него, с адресом связности из связки;
- для нового поведения — лёгкий RED/GREEN, для рефакторинга — зелёное покрытие; у risky — доказательство регрессии; строка «Подразумевается, но не проверено тестами»;
- противоречия со связкой — первой строкой «Риск: связка расходится с <base, решением владельца в `epic.md` или постановкой>: … — предлагаю …»; связку не правит и не обходит молча, решает оркестратор.

Сценарии «дано — когда — тогда» должны быть в карте продукта до кода. В части «Суть» назови полосу: полоса из постановки подтверждается или правится по признакам п. 2. Полосу выбирай самую дешёвую, какую спека выдерживает: допиши в спеку фрагмент или решение, чтобы тикет ушёл ниже; complex — одной строкой скажи, какое решение спека назвать не может. В спеке тикета общий контекст не повторяй, ссылайся на `epic.md`. Волна из одного тикета — связки нет, спека тикета самодостаточна. Сообщи состав связки либо существенные изменения и ограничения спеки тикета. Одиночная задача вне эпика — одна спека `<specs>/<проект>/<ГГГГ-ММ-ДД>-<тема>.md`, её пишет исполнитель или главная сессия.
